# Capture implementation and validation boundary

`ios/ReverseCAD/CaptureARKit.swift` implements live acquisition. `CaptureController.swift` owns the SwiftUI adapter, foreground-selection mapping, and replay provider. `packages/ReverseCADCore` owns the portable contract, geometry, package integrity, interrupted-capture recovery, and service upload client.

One `ARSession` produces camera RGB, native `sceneDepth`, native confidence, intrinsics, monotonic capture timestamps, and the visual-inertial camera transform. No accelerometer integration or second camera session produces pose. Hardware capability checks select live LiDAR, limited camera/manual capture, or replay. Simulator replay never constructs an `ARFrame` and never claims to validate a sensor.

The default budget is 90 seconds, at most 240 persisted keyframes (accepted and rejected combined), at most 80 rejected records, and 512 MiB. A 16 MiB reserve leaves room for final metadata. At most two retained CV buffer sets can be awaiting encoding. Optional motion work has eight slots. Slow encoding/segmentation drops frames with counters, rather than retaining an unbounded ARFrame queue. File encoding, segmentation, checksumming, and movie writes occur off the main and ARSession callback queues. Low storage stops capture and preserves committed frames.

Keyframe selection uses pose translation, angular change, elapsed overlap interval, tracking state, a sampled luma Laplacian detail score, depth availability, and confidence support. Camera-direction bins are a relative observation diagnostic, not a percentage of reconstructed or hidden surface coverage. Low image detail can indicate either blur or low texture. The threshold is an initial quality heuristic and must be evaluated on the phone.

Depth Float32 values retain native meters, including invalid values that the reconstruction filters explicitly. The copier respects each CV buffer's row stride, then persists tightly packed rows with little-endian metadata. Confidence labels are 0 low, 1 medium, 2 high. An absent confidence map is recorded as absent; no confidence data are invented. The original-resolution JPEG, raw-image `.up` orientation, original calibration resolution, and column-major `T_world_camera` remain paired with every keyframe.

Native ARKit depth and RGB are related by direct calibration scaling: `fx`, `fy`, `cx`, and `cy` scale with depth resolution divided by calibration resolution. This follows Apple's [point-cloud sample](https://developer.apple.com/documentation/arkit/displaying-a-point-cloud-using-scene-depth), specifically `MetalPointCloud.swift`. Synthetic fixtures generated through image resizing use the separate pixel-center convention `(c + 0.5) × scale − 0.5`. The versioned frame field `depth_calibration_mode` distinguishes these modes; old replay fixtures default to `pixel_center`. Never apply a portrait viewport transform to raw camera calibration. A tap in the live viewport is mapped through the inverse ARFrame display transform before selecting the Vision instance.

Vision foreground-instance masks use the tapped object or initial image center. A background/no-instance selection leaves the mask absent instead of claiming a reliable segmentation. The review crop and contact annotations provide user correction. Optional scene mesh reconstruction is only a visualization aid; native depth remains the measurement input.

The H.264 review movie uses the same ARKit RGB buffers, with bounded 1280-pixel long edge and 15 fps input target. `video/timestamps.jsonl` maps every appended movie presentation time to its original capture time. The full-resolution paired JPEG/depth files remain the calibrated evidence. Movie output is intentionally raw sensor orientation. Movie failure and incomplete-video status appear in `capture_diagnostics.json`; a playable movie is never inferred solely from the presence of a `.mov` file.

Optional CoreMotion device-motion logging records separate user acceleration and gravity in g, angular velocity in radians/second, quaternion attitude, its reference frame, and monotonic timestamps. ARKit and CoreMotion share a monotonic clock in memory. Before persistence, every frame, movie mapping, motion sample, callback and interruption timestamp subtracts the first ARFrame timestamp. This common offset preserves pairing and relative durations while keeping device uptime and the offset off disk and off the network. Motion samples preceding the first ARFrame are omitted. Diagnostics schema 2 identifies this clock as `seconds_since_first_ARFrame`; legacy/replayed packages retain their existing declared timestamps. These samples are diagnostic only and never enter pose fusion as independent measurements.

Interrupted or uncertain relocalized origins begin new unregistered segments. Reconstruction must reject those segments until an explicit registration is supplied. A return to normal tracking does not silently restore the old transform. Starting a fresh scan is the first-trial recovery route when registration evidence is unavailable.

Each frame's assets precede an atomic metadata checkpoint. Incomplete packages can recover committed frames after app restart. Recovery does not create missing sensor observations or mark a damaged movie complete. Replay validates file paths, dimensions, checksums, calibration, and frame identity, then writes the same CaptureFrame contract through the common package writer under a new scan ID.

Automated tests cover independent analytic camera rays and units, asymmetric transform serialization, CVPixelBuffer padding, missing/invalid observations, frame/package integrity, recovery, byte-exact replay, and real AVAssetWriter movie output/timestamp mapping. Generic device compilation checks the live API code. These checks do not establish real LiDAR calibration, foreground selection quality, VIO performance, thermals, phone throughput, metric accuracy, or printed fit. Those require the trials in `PHONE_TEST_PLAN.md`.
